# 评估与 Bad Case 迭代

语义问数不能只看 SQL 有没有报错。项目把正确性拆成几个可检查的环节：是否解析到正确指标和维度、模型字段映射是否可用、SQL 是否只读且符合映射、结果是否正确，以及缺信息或遇到不支持语义时是否先澄清。

## 回放黄金问题集

黄金问题集在 `data/evaluation/cases.json`，包含数据集版本、问题、期望意图、期望指标和维度、预期结果或预期澄清。运行：

```powershell
.venv\Scripts\python.exe scripts\evaluate_agent.py
```

评估会调用与 Agent 相同的项目查询工具，并写入 `data/evaluation/latest-summary.json`。报告按案例列出语义解析、SQL 安全、结果正确、澄清行为和不支持查询处理状态，并汇总失败案例编号。当前数据集覆盖：

- GMV、订单数、销量及门店/商品维度；
- 跨订单和订单明细粒度的 GMV 防重复检查；
- GMV 按商品查询时的澄清；
- “销售”歧义，以及未建模的利润指标。

样例数据和人工核算值见 `data/expected-results.json`。评价问题及期望意图变更时，提高 `dataset_version`，并复核期望行与指标口径。

## 记录并查看 Bad Case

`app.bad_cases.record_bad_case` 会把问题、模型版本、语义计划、生成 SQL、失败类别和预期修正追加到 `data/evaluation/bad-cases.jsonl`。评估脚本会自动保留未支持或有歧义的查询案例。示例记录包括将订单级 GMV Join 到订单明细后求和的重复计算风险。

每次排查按以下顺序进行：

1. 用问题和版本号复现原始语义解析结果。
2. 检查 SPARQL 返回的指标定义、粒度、字段与 Join 关系。
3. 若语义计划正确，再查看生成 SQL、绑定参数和实际行。
4. 将错误归到本体/指标映射、意图解析、SQL 编译或数据样例中的具体一层。
5. 先加入黄金问题和期望修正，再修订对应层并重新运行评估。

模糊词汇应通过增加别名或明确澄清路径修正；错误 Join 应改语义关系或固定 SQL 编译模板；指标口径错误应更新模型版本，并重新校验、发布。不要只改最终回答文字来掩盖模型或查询层的错误。

## 解释分数和失败

“语义解析通过”表示请求已解析为预期指标/维度，或对预期不支持的请求明确拒绝。“SQL 有效”只适用于实际执行查询的案例；澄清案例不适用。结果比较忽略行顺序，但逐字段比较指标值和维度值。评估分数只代表当前合成数据集和词汇范围，不应当被解释成生产准确率。

若某案例失败，报告 `failed_cases` 会列出编号，每条记录也包含实际状态、实际结果及语义计划，便于定位错误发生在哪一层。修复后重复回放；通过后将模型、数据和评估集版本一并记录。
